# P1 核心业务闭环

## Goal

在不依赖线下表格补流程的前提下，让顾问、教务、教师和财务能够在系统内完成校区的主要日常业务；本父任务只负责阶段拆分、依赖关系和最终集成验收，不直接承载业务代码。

## Confirmed Facts

- GitHub Issue #6 已确认 P0 的仓库内交付完成；告警实际投递和真实恢复演练由 #23 独立跟踪，不阻塞 P1 开始。
- 既有 P1 基础能力已交付：机构与角色、学员档案、课程/班级/单次课次、入班/考勤/课消、报名续费/转课/退费/欠费跟进，以及站内通知、审计和导入导出。
- 当前 README/能力边界仍缺少独立报名、完整业务时间线、手工开单与冲正等能力；周期排课、批量生成、调课、补课和教室资源管理已交付。
- 现有教学模型以 `course -> classGroup -> lesson` 为事实边界；课次已具备教师与教室冲突校验，班级、报名和课次的既有状态契约不得破坏。
- 教师档案支持显式绑定成员账号；教师角色可在教师工作台读取本人课次、点名并记录课后结果，服务端继续限制为本人绑定课次。
- 既有课次完成动作已经原子写入考勤、课消和审计，因此教师工作台应复用该业务动作并只收窄到本人已绑定的课次，不能另建第二套点名或课消逻辑。
- 已确认：教师账号由管理员在教师档案中显式绑定至同机构、`teacher` 角色的成员账号；同一成员最多绑定一个教师档案。
- 当前排课支持单次与周期规则、批量生成、未来课次调整和请求幂等，并在事务内检查教师、教室和时间冲突；剩余演进集中在学员/报名与财务闭环。
- 已确认：首期仅支持有效日期范围内、按每周选定星期和固定开始时间/教室生成课次；隔周、自定义间隔、节假日例外等复杂周期语义不在首期实现范围，但周期规则和生成接口应预留可扩展边界。
- P1 剩余能力跨数据库、API 与 Web，必须拆成可独立验收的子任务；当前父任务已完成教务 T1/T2，继续跟踪 #25–#29。

## Requirements

### R1. 子任务拆分与顺序

- 以“周期排课、未来课次批量变更与教师工作台”为第一个子任务：补齐重复排课、未来课表调整，并让教师可以查看本人课表、点名和记录课后结果。
- 后续按依赖拆分为：教务停复课/补课与资源管理、独立报名与业务时间线、报名状态变更与学员合并、财务手工开单与调整、退款审批/冲正与凭证输出。
- 每个子任务必须单独定义数据库变更、授权、审计、兼容性、验证及回滚策略；其中资金和课时变化需要在同一事务内完成并可追溯。

### R2. 跨任务约束

- 所有查询和写入都以服务端解析的机构、成员角色和校区范围为准，不能信任客户端传入的机构边界。
- 教师工作台只能读取及完成已显式绑定到当前成员的课次；绑定、解绑和重复绑定必须由服务端校验并可审计。
- 金额继续使用分；排课、课次和业务时间线继续明确使用 `Asia/Shanghai` 时区。
- 变更必须通过 Zod API 契约、数据库集成测试和对应 Web 操作入口闭环；不得只新增后台数据结构。
- 不将外部告警、真实恢复演练、在线支付自动对账、外部触达、家长端、经营分析或开放 API 纳入本 P1 父任务。
