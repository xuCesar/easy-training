# P1 独立报名入口与原子建档开单

来源：GitHub Issue #25，父路线图 Issue #6，父任务 `p1-core-business-loop`。

## Goal

让顾问和校区管理人员无需先创建招生线索，即可从学员中心为已有学员办理报名，或在同一流程中原子创建新学员、主要联系人、报名与应收账单；后续继续复用现有财务收款入口。

## Confirmed Facts

- 当前唯一完整报名入口是线索转化；其契约要求 `leadId`，并支持选择已有学员或创建新学员、可选入班、设置购买课时、成交金额和账单到期日（`packages/api/src/contracts/training.ts:626`、`packages/api/src/contracts/training.ts:697`）。
- 线索转化已在单个 PostgreSQL 事务中锁定和复核线索、课程、校区、班级、容量与套餐权限，并创建学员、主要联系人、报名和账单（`packages/db/src/repositories/enrollment-conversion.ts:318`）。
- `enrollment.leadId` 已允许为空；现有唯一索引只约束机构与非空线索组合，因此数据库模型可表达独立报名（`packages/db/src/schema/training.ts:892`）。
- `invoice.enrollmentId` 可关联报名，账单金额使用整数分，收款仍通过独立财务入口处理（`packages/db/src/schema/training.ts:1218`）。
- 学员写权限当前覆盖 `owner / admin / campus_manager / consultant`，并在 repository 事务内重新读取成员角色与校区授权，不能只信任 API 上下文快照（`packages/db/src/repositories/students.ts:107`）。
- 线索报名仅允许 `owner / admin / campus_manager` 修改课程标准价格或课时，`consultant` 必须使用课程标准套餐；独立报名应保持相同边界（`packages/api/src/repositories/enrollment-conversion.ts:20`）。
- 现有 Web 学员中心已具备新增/编辑学员弹窗；线索页已有完整报名表单和加载、错误、提交中、成功反馈，可复用其交互与校验模式，而不能复用带 `leadId` 的提交契约。

## Requirements

### R1. 独立报名入口

- 在学员中心提供明确的“办理报名”入口。
- 支持选择已有学员，也支持在报名流程内创建新学员及一位主要联系人。
- 新学员至少录入姓名、所属校区、主要联系人姓名和手机号；状态默认有效，非报名必需资料可在学员档案中后补。
- 已有学员仅允许“试听、在读、需关注”状态直接报名；暂停或已结业学员必须先走后续生命周期恢复流程，不在本任务中隐式改写状态。
- 支持选择启用课程、可选的可报名班级、购买课时、成交金额和账单到期日。
- 允许暂不分班；后续继续使用现有班级分配能力。
- 同一学员已有同课程有效报名时，禁止再创建新的有效报名，提示使用续费；转课、复课等状态变化由后续流程处理。

### R2. 业务规则复用

- 课程必须属于当前机构且处于启用状态。
- 班级必须属于所选课程和学员校区，状态为可招生或进行中，并满足班级容量和未来课次教室容量约束。
- 停用校区、越权校区、跨机构资源、满班、暂停/结业班级及重复入班均由服务端拒绝。
- `owner / admin / campus_manager` 可按现有规则覆盖标准课时和价格；`consultant` 必须使用课程标准套餐。
- 独立报名创建的 `enrollment.leadId` 必须为 `null`，不得伪造或隐式创建招生线索。

### R3. 原子性、幂等与审计

- 新学员路径在同一数据库事务中创建学员、主要联系人、报名、可选入班和应收账单；任一步失败不得留下部分数据。
- 已有学员路径在同一事务中锁定并重新校验学员、成员校区授权、课程、班级和容量。
- 提交必须携带 `requestId`；机构内同一请求与相同输入重放返回原结果，不新增报名、账单或审计；相同 `requestId` 与不同输入返回明确冲突。
- 服务端在事务内重新读取当前成员角色和校区授权，防止权限撤销与提交并发竞态。
- 成功创建需写入机构审计，包含操作者、学员、报名、账单、课程、班级和必要金额/课时摘要，不记录完整联系人手机号。

### R4. API 与 Web 闭环

- 新增独立报名选项与提交契约，和线索转化共享稳定的领域校验与结果结构，但不把可空 `leadId` 强行塞入现有线索 API。
- 成功后刷新学员、班级、财务账单及相关工作台数据，并提供继续登记收款的现有入口或明确跳转。
- 覆盖加载、空数据、错误、字段校验、提交中防重复、成功反馈和桌面/移动端布局。
- 保持现有线索转报名行为、历史数据和 API 兼容。

## Acceptance Criteria

- [ ] 可为当前机构和授权校区内的已有学员直接创建报名与应收账单，全程不创建线索。
- [ ] 可在同一流程原子创建新学员、一位主要联系人、报名和应收账单，并可选择立即入班或暂不分班。
- [ ] 独立报名的 `leadId` 为 `null`；失败、重试或并发提交不会产生孤立学员、重复报名、重复账单或重复审计。
- [ ] 跨机构、越权校区、停用课程/校区、班级不匹配、满班、未来课次教室超容、重复入班和套餐越权修改均由服务端拒绝。
- [ ] `consultant` 只能使用标准套餐；管理角色可沿用现有改价/改课时能力。
- [ ] PostgreSQL 集成测试覆盖已有/新学员、暂不分班/直接入班、权限撤销、事务回滚、幂等重放和并发边界。
- [ ] Web 覆盖加载、空态、错误、提交中、成功跳转及桌面/移动端验证；现有线索转报名回归通过。

## Out of Scope

- 在线支付、首笔收款合并提交、退款审批、合同签署或发票开具。
- 学员/联系人模糊查重与合并；该能力继续由 #26 负责。本任务只沿用现有明确选择和手机号基础提示能力。
- 完整学员业务时间线；该能力继续由 #27 负责。
- 批量报名、跨机构报名、复杂折扣引擎和审批流。

## Planning Decision

- 同一学员已有同课程有效报名时，独立报名和线索转化均拒绝新建报名并提示使用续费，避免多个课时账户和账单的归属歧义。
