# Issue 30 教务排课体验、可访问性与模块化

## Goal

在不改变现有排课、调课、补课、考勤与课消业务规则的前提下，提升教务工作区的错误可见性、危险写入交互可靠性、无障碍可用性，以及前后端教学领域代码的可维护性。

## Confirmed Facts

- GitHub Issue #30 的范围包括：读取失败不得伪装为空态、危险写入提交中禁止关闭、编辑会话稳定复用 `requestId`、补齐 Select/复选框无障碍标签、兼容全角历史教室冲突、拆分 teaching/scheduling repository 与 `academic-workspace` 大文件、补教室/补课并发覆盖。
- `apps/web/src/features/training/academic-workspace.tsx` 同时承担课程、教师、班级、单次/周期排课、课次、报名和考勤工作流，已超过 2,500 行。
- `packages/api/src/repositories/teaching.ts` 仍承载多个教学子领域；现有 API 路由已经按 `packages/api/src/routers/training/` 渐进拆分，教学仓储可沿用该增量迁移策略。
- `.trellis/spec/db/backend/teaching.md` 已规定：`lesson` 是唯一排课事实；历史自由文本教室仍必须可读；教室写入、排课和补课需要遵循统一锁顺序并覆盖并发行为。
- 已有 #43 完成教务工作区按 tab 门控查询与长列表分页；本任务不得回退这些优化。

## Requirements

### R1. 查询失败状态

教务工作区中的读取失败必须显示明确错误状态和可重试入口，不能与“没有数据”空态混淆。

### R2. 危险写入交互

取消课次、停用/删除周期规则、批量调课、补课取消等危险写入在提交期间不得通过遮罩、Escape 或关闭按钮退出；失败后恢复可操作状态并显示既有错误反馈。

### R3. 编辑请求幂等

同一次编辑会话内重试请求必须复用同一 `requestId`；成功提交或关闭会话后，新会话生成新的 `requestId`。

### R4. 无障碍与历史兼容

教务 Select、复选框及相关输入必须具有可访问名称；历史课次的全角/半角教室文本在冲突比较时按统一规范化规则处理，不修改已存历史文本。

### R5. 并发与数据一致性

补课、教室写入与排课的并发路径必须继续遵守既有锁顺序，并补足覆盖容量、启停或排课冲突的集成测试。

### R6. 渐进模块拆分

将教学仓储按稳定领域边界拆分为可独立维护的模块，并将 `academic-workspace` 的独立工作流拆为 feature 组件或 hooks；保持现有公开 ORPC 路径、业务语义和客户端行为兼容。

## Acceptance Criteria

- [ ] AC1：读取错误与空态在教务界面中可区分，并支持重试。
- [ ] AC2：危险写入提交期间无法意外关闭对话框；失败后仍可继续操作。
- [ ] AC3：编辑重试复用原始 `requestId`，关闭或成功后不会复用到下一编辑会话。
- [ ] AC4：相关 Select/复选框可由辅助技术识别；全角历史教室文本与等价半角文本可正确参与冲突判断。
- [ ] AC5：补课/教室/排课并发测试证明没有越过容量、启停或冲突校验。
- [ ] AC6：教学仓储与教务工作区按职责拆分，现有 ORPC 合同和已完成的 tab 门控/分页行为保持不变。
- [ ] AC7：每个独立子项单独提交，相关类型检查、静态检查和测试通过或记录受限原因。

## Out of Scope

- 变更排课、调课、补课、考勤、课消或容量计算的业务规则。
- 新增自动排课、拖拽日历、节假日规则或新的教学产品能力。
- 对历史教室文本进行数据回填或破坏性迁移。
