# P1 财务闭环深化（Issue #29）

## Goal

在现有不可变账单、收款、退款和欠费跟进基础上，补齐内部财务控制闭环：退款先审批、错误收款可冲正、欠费可按状态和周期处理、有效收款可生成唯一且可追溯的机构内凭证。

关联 GitHub Issue：[#29](https://github.com/xuCesar/easy-training/issues/29)

## Background

- 当前退款由财务角色直接登记，没有申请、审批、拒绝或取消事实。
- `payment` 与 `refund` 是正金额不可变流水；账单保存已收投影，退款不会删除或覆盖原收款。
- 当前欠费由未收金额实时推导，`invoiceFollowUp` 只有追加备注，没有处理状态和轮次。
- 当前没有收款冲正、收据或付款凭证模型。
- 所有新增写入必须延续机构/校区隔离、事务内重授权、整数分、幂等、行锁和同事务审计。

## Delivery Map and Order

父任务只维护源需求、跨任务不变量、依赖顺序和最终集成检查，不直接作为实施目标。子任务按以下顺序实施：

1. `07-21-refund-approval`：退款申请、审批、拒绝、取消与批准后原子退款。
2. `07-21-payment-reversals`：以不可变相反流水纠正具体错误收款；依赖退款审批的最终资金事实。
3. `07-21-arrears-workflow`：欠费状态、轮次和操作历史；依赖冲正重新产生待收的语义。
4. `07-21-receipt-documents`：唯一编号、凭证状态和打印输出；依赖退款与冲正的最终展示语义。

## Cross-task Requirements

- 退款审批、收款冲正、欠费状态和凭证不得删除、覆盖或重新指向既有账单、`payment`、`refund`、课消或账单调整事实。
- 账单 `paidAmountInCents` 表示扣除冲正后的有效收款投影；退款保持独立，不通过降低该投影重新打开应收。
- 账单存在任何已批准退款时禁止收款冲正；实际向家长退钱必须走退款审批，不能用冲正替代。
- 退款批准、冲正及其账单/报名投影更新必须原子完成；幂等重放和并发操作最多产生一份有效结果。
- 冲正使账单重新产生待收时恢复普通收款；后续到账创建新的 `payment`，不得恢复或改写原收款。
- 账单首次产生待收时自动进入“待跟进”；结清时自动“已解决”；再次产生待收时创建新一轮并重新进入“待跟进”。
- 凭证只引用稳定资金事实；退款和冲正不静默改写历史快照，必须在当前状态与关联流水中可追溯。
- 中央审计只记录白名单关键字段；申请、拒绝、取消、冲正、暂停追缴和作废等自由文本只保存在领域事实中。

## Confirmed Product Boundaries

- 退款申请角色为 `finance`、`campus_manager`、`admin`、`owner`；仅 `admin`、`owner` 可批准或拒绝，且申请人不得审批自己。
- 同一账单同时最多一条待审批退款申请；待审批不预占资金，批准时按最新余额重新校验。
- 收款冲正支持对具体 `payment` 多次部分冲正，累计不超过原收款；完全冲正后净额为零。
- “承诺付款”要求不早于当天的承诺日期；“暂停追缴”要求原因、恢复日期可选；“已解决”不能人工提前设置。
- 首版按单笔收款、由授权用户按需生成凭证；保留多笔合并、自动开具和服务端输出的扩展边界。
- 凭证编号为机构级 `RCP-YYYYMM-NNNNNN`；允许断号但不可修改或复用。
- 已生成凭证不可编辑或删除；通过“作废 + 新编号补开”纠正展示信息，同一收款同时最多一张有效凭证。
- 首版提供系统内详情、打印样式和浏览器打印/另存 PDF，不提供服务端 PDF、图片、邮件或批量打包。

## Acceptance Criteria

- [ ] 四个子任务均有可测试的 PRD、技术设计和实施计划，并按依赖顺序独立实施、检查和归档。
- [ ] 退款、冲正、欠费状态和凭证在 Web、API、DB 与机构审计中的语义一致。
- [ ] PostgreSQL 集成测试覆盖角色、机构/校区、幂等、并发、金额守恒、历史迁移和事务回滚。
- [ ] 退款批准与冲正并发、冲正与新收款并发时，不会产生双重扣减、超收或绕过审批。
- [ ] 相关类型检查、Biome、构建以及桌面/移动端实际交互与打印验证通过。

## Out of Scope

- 银行或支付平台原路退款、电子发票、会计总账、外部催收以及短信/微信通知。
- 已批准退款账单的通用历史差错修正。
- 多笔收款合并开具、自动开具配置、服务端 PDF、图片和批量导出。
