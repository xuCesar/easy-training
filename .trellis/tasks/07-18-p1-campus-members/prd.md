# P1 多校区与成员角色管理

## Goal

为多校区教培机构提供可管理、可审计且服务端强制执行的校区与成员授权能力，为后续学员、教务和财务模块复用统一的组织边界。

## Confirmed Facts

- 当前 `organization_member` 已保存机构、用户和角色，角色包括 `owner`、`admin`、`campus_manager`、`consultant`、`teacher`、`finance`。
- 当前机构与角色由服务端 session 解析，所有现有业务接口都不信任客户端传入的机构 ID。
- `campus` 已有机构、编码、名称、城市、地址、教室数和容量字段；没有启停状态或成员范围关联。
- 当前 roles 仅用于模块访问控制；未实现成员维护、校区访问范围、角色变更审计或邀请流程。
- 本期决定采用限时、一次性的受邀注册链接；当前仓库没有邮件发送服务或相关环境变量。
- 本期邀请由管理员复制链接并通过机构现有渠道发送；不引入邮件供应商、发送队列或邮件密钥。
- 课程、线索、学员、班级等领域已关联校区，因此校区停用必须保持历史可读并阻断后续写入。

## Requirements

### R1 校区管理

- 机构授权角色可以列出、新增、编辑、启用和停用本机构校区。
- 校区编码在机构内唯一；停用不删除历史数据。
- 业务写入必须拒绝使用停用校区，读取历史记录不受影响。

### R2 成员与角色管理

- 授权管理员可以查看本机构成员，并管理角色与成员归属。
- 管理员可创建、撤销和重发限时一次性邀请；受邀账号注册或登录后加入指定机构并取得预设角色与范围。
- 邀请管理界面必须明确展示链接状态和复制动作，不假设系统已经投递邮件。
- 邀请创建时必须填写目标邮箱；当前版本仅允许规范化后相同邮箱的账号领取。由于本期不接入邮件验证，此机制不能证明邮箱控制权，界面不得宣称可完全防止知晓邮箱的转发者冒领；严格邮箱验证作为可插拔后续能力保留。
- 邀请默认有效期为 7 天，管理员可以撤销；重发会撤销此前仍有效的邀请。
- 所有角色和成员变更均在服务端校验操作人的权限。
- 系统必须始终保留至少一名 `owner`；不得移除或降级最后一位 owner。

### R3 校区访问范围

- `owner`、`admin` 始终拥有全机构访问，不配置校区范围。
- `campus_manager`、`consultant`、`teacher`、`finance` 可拥有全机构访问或指定校区访问范围；没有范围时不能访问校区业务数据。
- 服务端必须在任何校区资源读取和写入时强制范围校验，不能依赖前端筛选。
- 范围变化不得影响历史归属数据。

### R4 审计与交互

- 校区启停、成员角色、成员范围和移除操作必须记录操作人、时间及前后值。
- 管理端需提供桌面与移动端可用的校区、成员管理流程，包含加载、空、错误、权限不足和危险操作确认状态。

## Acceptance Criteria

- [ ] 跨机构不能读取或修改校区、成员及成员访问范围。
- [ ] `owner`、`admin`、`campus_manager` 的管理策略由服务端强制；其他角色不能越权管理成员。
- [ ] 最后一位 owner 不能被移除或降级，并有集成测试覆盖并发或竞态边界。
- [ ] 停用校区后，线索、学员、班级等新增/变更写入会被拒绝；历史记录仍可读取。
- [ ] 校区范围限制可阻止越权访问和写入，关键路径有集成测试。
- [ ] 所有成员、角色、范围和校区启停操作具备可追溯审计。
- [ ] 数据库迁移兼容现有机构、校区和成员数据，提供可执行的回滚说明。

## Likely Out of Scope

- 薪酬、排班、考勤规则等人员管理能力。
- 组织树、区域层级与跨机构集团管理。
- 复杂的细粒度字段级权限系统。

## Planning Defaults

- `owner` 管理全部校区、成员、角色、范围和邀请；`admin` 管理校区及非 owner 成员；`campus_manager` 仅能查看其范围内的校区与成员摘要，不管理角色、范围或邀请。
- 校区停用立即阻止新建和变更的校区归属；既有记录和历史报表保持可读。
- 成员移除立即撤销当前机构访问；审计记录保留。
- 审计记录保存动作、操作人、目标实体、发生时间以及脱敏前后值快照，不存储邀请原始 token。
- 邀请链接使用 URL fragment 承载随机 token；领取通过 POST body 提交，服务端仅保存不可逆 hash，避免 token 进入访问日志、请求 URL 和审计日志。
