# 邀请列表重发入口优化

## 目标

让管理员只对当前可领取的邀请执行“重发”，避免同一邮箱的历史邀请与有效邀请同时出现等价操作入口。

## 背景与已确认事实

- 邀请列表在 `apps/web/src/routes/_auth/settings.tsx` 呈现操作入口。
- 现有 `canResend` 仅排除已领取邀请，因此已撤销或已过期的历史记录也会显示“重发”。
- 后端重发会撤销同邮箱仍有效的邀请并创建新链接；因此从历史记录点击“重发”会与当前有效邀请的操作产生歧义。

## 需求

- 仅当邀请未领取、未撤销且未过期时显示“重发”。
- “撤销”遵循同一有效邀请边界，避免对已过期记录提供无效操作。
- 不修改邀请创建、重发、撤销的后端契约或数据库数据。
- 不新增前端测试框架；使用现有类型检查与构建验证这项纯展示条件的改动。

## 验收标准

- [x] 已撤销、已领取、已过期邀请均不显示“重发”或“撤销”。
- [x] 待领取、未撤销且未过期邀请同时显示“重发”和“撤销”。
- [x] `pnpm --filter web check-types` 通过。

## 范围外

- 不改变历史邀请记录的保留和排序。
- 不提供从已撤销历史记录恢复邀请的单独入口。
