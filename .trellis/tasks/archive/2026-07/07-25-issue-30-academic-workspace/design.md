# Issue 30 技术设计

## 交付结构

本任务作为总任务，不直接承载业务代码。按可独立验证、可单独提交的边界拆为三个子任务：

1. 教学仓储兼容与并发保障：历史教室名称规范化和补课/教室/排课并发测试。
2. 教务工作区渐进拆分：将 `academic-workspace.tsx` 的稳定面板、编辑器和查询边界移至 feature 模块，保持路由与 ORPC 调用不变。
3. 教务交互可靠性与无障碍：在拆分后的组件中补齐查询错误态、危险写入关闭保护、编辑会话 `requestId` 生命周期和可访问名称。

## 边界与兼容性

- `packages/db` 继续是排课事实、冲突判断、锁顺序和事务行为的唯一实现位置；不移动 SQL 至 API 或前端。
- 既有 `training.teaching.*` ORPC 路径、Zod 合同、返回字段和错误映射保持不变。
- `lesson.room` 与历史规则中的自由文本仍原样保存与展示。仅在比较冲突键时应用 Unicode 规范化，不做数据迁移。
- 前端继续由 `/_auth/academic` 提供页面入口，并保留 #43 的按 tab 门控查询和 cursor 分页。

## 数据与并发

`normalizeRoom` 是历史自由文本教室的比较边界。其实现必须把等价全角/半角形式归一后再执行既有的 trim/case/space 规则。新增测试覆盖同一校区、等价文本和重叠时间的冲突拒绝，并断言原始历史文本未被写回修改。

补课、教室写入和排课继续使用现有“机构 advisory lock -> 当前权限重验 -> classroom 行锁”的顺序。测试只补覆盖缺口，不改变锁范围或业务容量口径。

## 前端状态模型

- 读取状态区分 `pending`、`error`、`empty`、`ready`；`error` 提供重试，不以空数组渲染为空态。
- 危险 mutation 的 `isPending` 是对话框关闭守卫：`onOpenChange`、Escape、外部交互和关闭按钮均不得在提交期间释放编辑状态。
- 编辑器打开时生成 `requestId` 并保存在会话状态/ref 中；同一会话重试复用，成功或关闭后释放。服务端既有幂等合同无需修改。
- Select 和复选框使用关联 `Label` 或 `aria-label`，不依赖占位文案作为名称。

## 回滚

每个子任务均为应用代码和测试调整，无 schema 或数据回填。回滚对应提交即可；历史文本、既有 API 合同和数据库事实不受破坏。
