# P1 报名状态流转与学员联系人查重合并

来源：GitHub Issue #26，父路线图 Issue #6，父任务 `p1-core-business-loop`；依赖已完成的 #25 独立报名入口。

## Goal

让教务能安全地变更未来待上课的报名与班级归属，并让运营人员能识别和人工合并重复学员/联系人；已消课的考勤、课消、收款和账单永远保持为可追溯的历史事实。

## Confirmed Facts

- `student.status` 已有 `active / trial / paused / graduated / at_risk`，但当前没有由生命周期动作驱动报名状态的服务端流程（`packages/db/src/schema/training.ts:92`）。
- `enrollment.status` 当前只有 `active / transferred`，报名可选关联 `classGroupId`，且已存在按报名完成点名和课消的事实记录（`packages/db/src/schema/training.ts:144`、`packages/db/src/schema/training.ts:909`）。
- 现有“转课”是财务语义：将剩余课时转到目标课程、来源报名改为 `transferred`，不是同课程的转班能力（`packages/db/src/repositories/enrollment-finance-adjustments.ts`）。
- 现有 `assignEnrollmentClass` 可修改有效报名的班级归属，但没有生命周期状态、未来课次影响、版本并发或独立审计边界（`packages/api/src/contracts/training.ts:1277`）。
- 已确认的全局事实边界：已经消课的课次冻结且可追溯，任何调整只能影响未来待上课次；这与 #26 的“账单、收款、考勤、课消永久保留”一致。
- 学员和联系人均保存原始联系电话；学员表已有 `(organizationId, guardianPhone)` 普通索引，但没有标准化手机号、查重提示、来源映射或合并审计模型（`packages/db/src/schema/training.ts:491`、`packages/db/src/schema/training.ts:520`）。
- #25 的独立报名会为新学员创建一位主要联系人，并已经在写入事务内重读成员、角色和校区范围；本任务必须延续同一授权边界。

## Requirements

### R1. 报名与班级生命周期

- 转班、退班、冻结与复课均以“单条报名”为作用主体；同一学员的其他课程报名完全不受影响。为每个动作定义允许来源状态、目标状态、角色/校区授权、请求幂等和并发版本校验。
- 转班仅允许转入同课程、同校区且可报名的目标班级；从转班操作时点起变更后续待上课次名单，必须校验目标班级和未来教室容量。已完成课次的实际班级、考勤和课消不回写，课表差异不自动补课。
- 退班仅解除该报名的班级归属，保留报名和剩余课时，可在之后重新分配到同课程、同校区的其他班级；终止课程报名、退款与转课不得混入退班。
- 冻结和复课只作用于未来可执行业务；不得删除或改写已有账单、收款、考勤、课消和审计。
- 冻结与复课在操作时点立即生效：冻结后不再进入之后的待上课次名单；复课只进入复课时点之后的课次，不自动补课、补扣或回写冻结期间及更早的历史。
- 明确冻结/退班后的点名和课消边界：未来课次不得再进入可点名名单；复课不会补造或重写历史。实现必须保存生命周期生效区间，使复课不会重新加入冻结期间已生成但尚未完成的课次。

### R2. 查重与人工合并

- 在创建学员、编辑联系人和独立报名的新建学员路径中，按同一机构的标准化手机号返回“疑似重复”提示：去除空格、横线、括号并统一 `+86` / `86` 前缀后，比较学员监护人和全部联系人号码。允许跨校区提示，姓名和生日仅作人工判断辅助；不自动阻止创建或自动合并。
- 提供人工合并：操作者选择主档案，系统仅迁移可安全归并的联系人、标签和业务关联；源档案保留来源映射、禁止再次参与业务写入，并写审计。
- 不可自动合并的冲突字段必须由操作者显式选择，禁止静默覆盖；不同机构数据绝不参与匹配。
- 人工合并仅限 `owner` / `admin`；两个档案必须属于当前机构，且操作者对两个学员校区都具备写权限。合并后源档案转为只读来源映射，禁止报名、编辑或参与任何业务写入。
- 若两个档案存在同一课程的有效报名，必须阻止合并并提示先通过续费、转课、退班或财务流程显式处理其中一条报名；不得静默叠加课时账户、账单或未来名单。
- 合并预览默认主档案值，但姓名、所属校区、出生日期、学员状态和主联系人发生冲突时必须由操作者显式选择；联系人按标准化手机号去重，其余联系人与标签取并集。

### R3. 数据安全与闭环

- 所有命令在单一服务端事务内重新校验机构、成员、校区、资源状态、版本与并发；失败不留下部分事实。
- 所有生命周期和合并动作具备独立、可追溯的审计记录与 request ID 幂等边界。
- Web 提供明确入口、风险说明和系统风格二次确认，覆盖加载、空态、错误、提交中、移动端及成功后的数据刷新。

## Acceptance Criteria

- [ ] 非法状态跳转、越权、陈旧版本和并发重复操作被明确拒绝，且无部分写入。
- [ ] 转班、退班、冻结与复课不改写历史课次、考勤、课消、账单或收款；只影响未来业务。
- [ ] 冻结/退班后，未来课次不能继续点名或课消；复课仅从之后的可用未来课次恢复。
- [ ] 创建与独立报名时只提示同机构疑似重复；不同机构不匹配，也不自动合并。
- [ ] 合并后业务事实、账单、收款、报名、考勤和课消全部仍能按主/源档案追溯；源档案不可再报名或写入业务。
- [ ] PostgreSQL 集成测试覆盖状态矩阵、容量、权限、版本/幂等并发、合并守恒和事务回滚；Web 覆盖危险操作确认与移动端。

## Out of Scope

- 跨机构合并、自动模糊姓名判断、批量合并、删除或重写财务/教学历史。
- 在线支付、退款审批、账单调整与凭证输出（分别由 #28、#29 跟踪）。
- 结业工作流，以及自动根据“长期未上课”推断冻结或退班。

## Confirmed Decisions

- 同一学员可拥有多门课程，且每条报名独立流转：冻结、复课、退班和转班只影响被操作的单条报名，不影响其他课程。
- 冻结与复课按操作时点立即生效；复课只重新纳入之后的未来课次，不自动处理冻结期间课次或课时。
- 退班是班级归属变更，不是终止报名：保留该报名的剩余课时，后续可重新分班；课程终止与资金处置沿用独立财务流程。
- 转班仅限同课程、同校区并从操作时点起影响后续待上课次；历史事实不回写，课表差异仍需显式使用补课流程。
- 疑似重复以同机构标准化手机号为唯一触发条件，比较监护人和全部联系人号码；允许跨校区提示，不匹配其他机构；姓名和生日只辅助人工选择，不自动合并。
- 人工合并仅允许 owner/admin 操作同机构且双校区均有写权限的档案；源档案保留映射和审计，但不可再写入业务。
- 同课程有效报名是合并阻断条件，必须先单独处理冲突报名，不能自动合并课时、账单或未来名单。
- 合并冲突不得静默覆盖：姓名、校区、生日、学员状态和主联系人由操作者显式选定；联系人按标准化手机号去重，其他联系人和标签取并集。
- 本期不新增或强制使用“结业”动作。现有 `student.status = graduated` 仅为历史兼容和人工档案字段；课程是否完成由报名剩余课时、未来课次和续费行为表达，不能把“暂不续费”隐式写成结业。
