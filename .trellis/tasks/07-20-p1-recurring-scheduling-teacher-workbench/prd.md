# P1 周期排课、未来课次调整与教师工作台

## Goal

让教务能够按周生成并安全调整未来课次，让已绑定账号的教师完成本人课表、点名和课后记录；继续以 `lesson` 作为唯一课次事实源，保证未来安排可调整、已发生教学事实不可改写、考勤课消与授权边界可追溯。

## Background

- 现有系统已具备课程、教师、班级、单节课次、教师/教室冲突、课次取消，以及考勤、课消和结课审计。
- 当前排课只能逐节创建，没有周期规则、批量生成、未来课次批量调整或生成幂等保护。
- 教师档案已有可空 `userId`，但没有成员账号绑定入口；教师角色目前只能看到工作台近期课次摘要，不能保存点名或结课。
- 当前点名与结课是一次提交，保存考勤会立即产生课消并冻结课次，不能支持课中点名草稿。

## Requirements

### R1. 周期规则与批量生成

- `owner`、`admin` 和有权校区的 `campus_manager` 可为 `recruiting` 或 `running` 班级维护周期规则。
- 首期规则仅支持 `Asia/Shanghai` 下的有效日期范围、每周一个或多个星期、固定开始时间和固定教室；结束时间由课程标准时长计算。
- 一个班级允许维护多条有效规则，以表达不同星期、开始时间或教室；每条规则独立生成、同步并追踪关联课次。
- 周期模型和生成接口必须保留规则类型、间隔和例外扩展边界，但首期不实现隔周、自定义间隔或节假日例外。
- 生成必须先展开可编辑预览，标记与既有课次及候选课次之间的教师/教室冲突。预览单项只允许调整日期/开始时间和教室，教师与校区继承班级。
- 所有候选无冲突后才允许一次性提交。服务端在事务中重新校验权限、班级/校区/课程状态、教师校区归属、时长、重复和资源冲突；任一失败不得留下部分课次。
- 生成始终由教务明确发起、预览和确认，不由后台任务静默创建。课次实例必须可追溯到生成规则和规则版本，重复提交必须幂等。

### R2. 规则修改与停用

- 修改规则时必须指定生效日期，并预览该规则关联的未来 `scheduled` 课次。未被人工单独调整的课次默认同步新规则；例外课次必须明确标记，由教务选择保留例外或重新套用规则。
- 同步只能影响开始时间仍在未来的 `scheduled` 课次。已结课、已取消以及开始时间已经过去的课次永久保持原事实。
- 停用规则时先检查是否存在该规则关联、提交时仍为 `scheduled` 且开始时间晚于当前时间的未来待上课次：
  - 不存在：直接停用并停止后续生成。
  - 存在：询问是否同时取消未来课次。
  - 选择取消：必须填写本次批量取消的统一原因，预览后将原因逐节留存，并把关联的未来课次批量标记为 `cancelled`。
  - 选择不取消：仅停用规则，已生成的未来课次保持不变。
- 规则停用后不得继续生成或同步课次；恢复生成必须先通过后续显式启用流程，不允许提交接口隐式启用。
- 停用、同步和批量取消均不得物理删除规则或课次。

### R3. 任意未来课次批量变更

- 教务可从有权访问的未来 `scheduled` 课次中任意选择多项，不要求来自同一班级或周期规则。
- 允许修改日期/开始时间、教室和教师；结束时间由课程标准时长计算。班级、课程和校区不可修改，改派教师必须已归属课次校区。
- 教师和教室支持批量应用到全部选中项；时间支持统一偏移；预览中允许逐条覆盖日期、开始时间、教师或教室。不得把多节课设置为同一个绝对日期时间。
- 预览必须展示原值、新值、人工例外和冲突。提交时服务端以当前时间和数据库状态重新校验；任一课次已开始、状态改变、越权、教师不匹配或发生冲突时整批回滚。
- 每节被调整课次必须记录操作者、批次请求和白名单前后值；已结课、已取消和开始时间已经过去的课次不可通过此流程修改。

### R4. 教师账号绑定与工作台

- `owner/admin` 可在教师档案中显式绑定或解绑同机构、当前角色为 `teacher` 的成员账号；同一成员最多绑定一个教师档案。
- 服务端拒绝跨机构、非教师角色和重复绑定；教师工作台同时校验当前成员角色和教师绑定，不能只按 `userId` 查询。
- 已绑定教师只能读取本人未来课次、可操作课次和近期历史；未绑定教师显示明确不可用状态，不得回退到机构级教务数据。
- 教师只能读取并操作本人课次的名单、点名草稿、可选教学小结和最终结课。管理角色保留既有校区范围内的教务操作能力。

### R5. 点名草稿、快捷结课与冻结事实

- 点名采用“草稿可选、快捷结课”：全勤班级可在课后一步执行“全勤并结课”；异常场景可先保存点名草稿再确认结课。
- 点名界面默认全员到课，支持修改少量迟到、缺勤或请假，并支持每名学员备注。草稿可反复保存，不扣课时、不冻结课次。
- 草稿从计划开始时间前 30 分钟开放；最终结课仅在计划结束时间到达后开放。提前下课可先保存草稿；逾期未结课仍可补结课并记录实际提交时间。
- 最终提交前显示到课/迟到/缺勤/请假人数和预计课时扣减，并允许填写一段可选的课次级教学小结；不包含作业或个体学习反馈结构。
- 最终结课必须锁定班级及当前 active 报名全集。若草稿后名单变化，必须要求刷新并重新确认，不得按陈旧名单扣课。
- 结课继续在一个事务内写入最终考勤、`present/late` 课消、教学小结、课次 `completed` 状态和审计。结课成功后，时间、地点、教师、考勤、课消和教学小结永久只读。

### R6. 安全、审计与兼容

- 所有写入从服务端会话解析机构、成员、角色和校区范围，并在机构事务锁内重新校验；不接受客户端提供的机构边界或“未来课次”判定。
- 周期规则创建/修改/停用、批量生成、未来课次调整/取消、教师绑定/解绑和最终结课必须可审计；自由文本学员备注和教学小结不得进入审计快照。
- 既有单节创建、课次取消、班级状态、报名、考勤、课消和运营工作台保持兼容；`classGroup.scheduleText` 继续只是派生兼容摘要，不能成为第二套排程事实。
- 时间输入、预览和显示统一按 `Asia/Shanghai`，存储使用带时区时间戳；不新增运行时依赖。

## Acceptance Criteria

- [ ] 一个班级可维护多条每周规则，并通过可编辑预览原子、幂等地生成无冲突课次；每节课次可追溯到规则及版本。
- [ ] 修改规则可按生效日期同步关联的未来待上课次并处理人工例外；停用规则严格遵循“检查未来课次 → 选择是否取消 → 必填原因或仅停用”的流程。
- [ ] 教务可任意选择有权访问的未来待上课次，批量应用教师/教室、统一时间偏移并逐条修正；任一并发状态或冲突变化都会使整批回滚。
- [ ] 已结课、已取消和开始时间已经过去的课次不能被规则同步或批量变更；已结课课次的教学、考勤和课消事实不可修改。
- [ ] 管理员可显式绑定/解绑教师成员；跨机构、非教师角色、重复绑定及失效权限均被服务端拒绝。
- [ ] 教师只能看到本人课次；全勤时可一步结课，异常场景可保存草稿。草稿不扣课时，只有计划结束后的最终结课产生课消、教学小结和冻结事实。
- [ ] 最终结课遇到 active 名单变化、余额不足、重复/并发提交或权限变化时不会产生部分考勤、课消、审计或状态更新。
- [ ] 数据库迁移、Zod 契约、API 授权、Web 桌面与移动端交互、PostgreSQL 集成测试、类型检查、代码检查和生产构建均覆盖受影响范围。

## Out of Scope

- 补课、班级级停课/复课、漏点名/漏结课修复流程和独立教室资源/容量目录。
- 隔周、自定义周期、节假日/调休自动例外、自动滚动生成和智能排课。
- 修改课次所属班级、课程或校区，以及修改任何已完成教学事实。
- 家长端、原生教师移动端、薪酬、作业、成绩和结构化个体学习反馈。
