# P2 运营效率与管理分析总体设计

## Architecture and Ownership

P2 沿用现有 monorepo 分层，不引入平行架构：

- `packages/db` 保存业务事实、不可变事件、有效期历史、报表计划与对象元数据，并在 repository 中执行机构/校区过滤、事务、锁和幂等。
- `packages/api` 用 Zod 定义统一契约，按角色选择允许的查询维度，将数据库领域错误翻译为稳定的 oRPC 错误；客户端不能指定机构边界。
- `apps/web` 提供全局搜索、批量操作、任务和分析页面，只渲染服务端已裁剪的数据，不在浏览器重复计算指标口径。
- 站内通知、机构审计、现有 CSV 约束、财务和课时不可变事实继续作为共享基础，不复制第二套通知、审计或资金账本。

父任务只维护公共规则和最终集成。每个子任务拥有自己的迁移、契约、实现、测试与回滚说明，按 T1 至 T7 分阶段交付。

## Shared Data Principles

- 机构和校区范围均由当前会话的成员关系在服务端解析；页面、导出、保存条件和定时报表执行时都重新授权。
- 当前归属与历史分析事实分开：负责人、容量等可变配置使用有效期历史或分配历史；转化、课消、资金、续费机会等经营事实不可静默改写。
- 事件区间统一为左闭右开，业务自然日按 `Asia/Shanghai`；金额使用整数分。
- 页面和导出复用同一查询服务与指标版本；前端只负责筛选、展示和受控下钻。
- 新表和新列均采用 additive migration，先兼容旧数据，再开启新写路径；不以破坏性迁移回算历史。

## Cross-Task Foundations

### Authorization

角色可见性集中在服务端：owner/admin 为全机构，campus_manager 为授权校区，consultant 为本人招生与脱敏基准，finance 为授权校区财务，teacher 为本人授课。子任务可以收窄但不能放宽该矩阵。

### Scheduler

T2 首次建设 PostgreSQL 驱动的到期提醒执行基础：持久化执行时间、数据库租约、幂等键和失败记录。T7 复用同一执行器增加报表计划，不再建设第二套调度器。P2 不依赖外部消息队列或任意 Cron 表达式。

### Private Object Storage

T4 建立私有 S3 兼容对象存储、隔离/扫描/清理状态和短时授权。T7 只消费该能力保存报表结果，不直接接触存储凭证或公开 URL。

### Metric Versioning

T5 固化核心事实与指标定义，T6 复用并扩展对比维度，T7 记录报表运行时的指标版本。不得由多个页面分别实现同名指标。

## Delivery Graph

1. T1 全局搜索，先降低跨模块查找成本。
2. T2 运营任务与提醒，建立任务闭环和通用调度基础。
3. T3 学员批量操作，降低重复录入和逐条维护成本。
4. T4 附件管理，建立私有对象与安全扫描边界。
5. T5 核心经营指标，先固化事实和口径。
6. T6 经营对比与资源/财务分析，复用 T5 指标基础。
7. T7 报表导出、保存条件和定时报表，依赖 T4、T5、T6。

T1 后续在 T2、T4 完成后以小范围扩展接入任务和附件；这不阻塞 T1 首次归档。

## Compatibility, Rollout and Rollback

- 每个子任务单独生成并审查 migration，应用代码先兼容空字段/无历史数据，再切换新入口。
- 分析功能先以只读方式上线，并提供数据成熟度、未配置容量和未分配归属提示；不伪造历史填充。
- 定时能力上线前先验证单实例与多实例租约、重启补偿和幂等；出错时可停用计划而不删除运行记录。
- 对象存储或扫描器不可用时，附件上传保持关闭，既有业务核心流程继续可用。
- 回滚应用时保留新增事实、任务历史、附件元数据和报表运行记录；不得用逆向迁移删除已产生的业务数据。

## Key Trade-offs

- 首期使用 PostgreSQL 的受限查询而非搜索引擎、数仓或 BI，减少运维面；若未来基于真实慢查询证据再引入索引或专用基础设施。
- 任务提醒和定时报表都采用数据库租约，适合当前规模并保证多实例唯一；不提前引入队列系统。
- 管理指标优先准确、可追溯和权限一致，不以展示更多数字为目标；缺少分母或成熟观察窗时返回不可比较语义。
