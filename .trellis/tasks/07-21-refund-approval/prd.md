# 退款审批闭环

## Goal

将当前“直接登记退款”改为先申请、后审批的受控流程；只有批准动作才能在同一事务中创建不可变退款流水并更新财务投影。

## Background

- 当前财务四角色均可直接调用退款接口。
- 当前仅已结清账单可退款，支持部分或全额退款；全额退款将账单标记为 `refunded`。
- 退款金额、报名累计已收和中央审计在同一事务中更新；退款原因不进入中央审计。
- 当前没有申请人、审批人、拒绝、取消、审批版本或操作历史。

## Requirements

- 新增退款申请及不可变操作历史，保存账单、申请金额、退款时间、方式、原因、申请人快照、校区、请求标识与创建时间。
- 申请当前状态为“待审批 / 已批准 / 已拒绝 / 已取消”，终态不可回退；同一账单同时最多存在一条待审批申请。
- `finance`、`campus_manager`、`admin`、`owner` 可提交；仅 `admin`、`owner` 可批准或拒绝，且申请人不得审批自己的申请，不提供单 owner 例外。
- 申请人可取消自己的待审批申请；`admin`、`owner` 可取消任意待审批申请。
- 批准意见可选；拒绝原因必填；申请人取消自己的申请时原因可选；管理员取消他人申请时原因必填。
- 待审批不改变、不预占账单、报名、课时或可退款余额，只阻止该账单继续提交新申请。
- 批准时锁定申请和账单，事务内重新校验审批权限、校区状态、申请版本、账单状态及最新可退款余额；余额不足或状态变化时整个操作失败。
- 批准必须复用现有退款金额守恒与报名累计已收重算规则，在同一事务中创建恰好一条 `refund` 并进入批准终态。
- 创建、批准、拒绝和取消分别幂等；相同请求不同载荷冲突，并发决策最多一个成功。
- 现有直接退款 API 与 Web 入口必须被替换，不能绕过审批。
- 全额退款后账单和审批历史仍可通过“已退款”筛选或稳定详情入口查看；默认未结清视图不展示已退款账单。
- 自由文本申请原因和操作意见保存在领域历史；中央审计只保存申请/退款标识、金额、状态、操作者、时间、校区和请求标识。

## Acceptance Criteria

- [x] 授权用户可提交部分或全额退款申请，并查看当前状态及完整操作历史。
- [x] 同一账单无法并存两条待审批申请；待审批不影响账单余额或报名累计已收。
- [x] 申请人不能审批自己；越权、跨校区、停用校区及提交后撤权均由服务端拒绝。
- [x] 拒绝或取消不产生退款；批准恰好创建一条退款流水并保持账单与报名金额守恒。
- [x] 陈旧版本、重复请求、并发审批和批准时余额变化返回明确错误且无部分数据。
- [x] 全额退款不会使账单、申请、审批和退款历史失去可访问入口。
- [x] 中央审计不包含申请、拒绝或取消的自由文本。

## Dependencies and Out of Scope

- 本任务为 Issue #29 的第一个实施子任务，无前置子任务。
- 不接入银行或支付平台，不提供自动审批，不允许修改已提交申请，也不处理已批准申请的撤销。
