# P0 生产安全与状态边界

## Goal

按 GitHub Issue #6 的 P0 路线图，消除现有功能的已知契约、状态边界和生产安全缺口，使资金、课时和权限变更可追溯，并让仓库具备可重复验证与基础恢复准备。

## Confirmed Facts

- 当前 `develop` 的类型检查、Biome 与 27 项 PostgreSQL 集成测试均通过；该基线不能替代新增 P0 边界的回归测试。
- CSV 导入前端与 API 内容约束为 500,000，而服务端 RPC body limit 为 256 KiB，导致合法前端输入可能在到达业务校验前被拒绝。
- 机构审计已覆盖校区、邀请、成员、线索导入导出与通知；收款、退款、续费、转课、结课尚未写入统一审计。
- 邀请领取只比较会话邮箱与受邀邮箱；用户模型已有 `emailVerified`，但当前领取路径没有使用它。
- 当前服务端仅使用 Hono 文本 logger 和 `console.error`，没有结构化事件、请求关联 ID 或关键事务失败记录；仓库也没有 CI 工作流或已验证的备份恢复脚本。

## Requirements

### R1：请求与导入契约

- 为 CSV 导入定义一个前后端一致、能考虑 JSON RPC 包装开销的大小边界。
- 前端预校验、API 契约、服务端 body limit 与业务解析必须返回一致且可理解的超限语义。
- 为边界内、边界外和绕过前端的请求补回归测试。

### R2：关键状态边界

- 明确班级状态可达迁移，拒绝不符合当前业务阶段的状态跃迁。
- 已转课或其他非有效报名不得重新入班、出现在待结课名单中，或消耗课时。
- 状态边界在 DB repository 事务内强制执行，并使用 PostgreSQL 集成测试覆盖重复、并发及跨机构/校区路径。

### R3：关键业务审计

- 收款、退款、续费、转课、结课与成员权限调整均需在同一业务事务内生成审计事件。
- 审计事件须包含操作、机构、操作者、实体和经白名单过滤的必要快照；不得记录 token、完整敏感联系方式或支付敏感信息。

### R4：邀请邮箱控制权

- 领取邀请必须证明当前会话的邮箱已验证且与受邀邮箱规范化后一致。
- 不能以降低验证要求来绕过该约束；若现有认证配置没有邮件验证流程，应提供安全的配置/运维前置条件与明确用户提示。

### R5：基础可观测性与交付保障

- 服务端关键请求和未预期失败使用结构化日志，具备稳定请求关联 ID，并在关键事务失败时保留不含敏感值的定位信息。
- 建立仓库可执行的 CI 基线（类型、规范、构建、集成测试）及数据库迁移检查。
- 提供数据库备份、恢复演练和应用回滚的可执行 runbook；任何依赖外部托管平台、密钥或备份存储的步骤必须明确标为部署前置条件，不能伪造已完成的外部保障。

## Acceptance Criteria

- [ ] P0 子任务以独立 PRD、设计、实施与验证记录推进，父任务记录跨任务依赖和集成结论。
- [ ] CSV 大小边界在前端、契约、服务端与测试中一致；超过边界得到 4xx 及可理解提示。
- [ ] 班级和报名状态不能通过 API 或直接 repository 调用进入不允许的后续写入路径。
- [ ] 六类关键写入均能按机构检索审计记录，且失败或重放不会产生错误审计历史。
- [ ] 未验证邮箱不能领取邀请；已验证且匹配的邮箱保留当前领取行为。
- [ ] CI 与数据库迁移检查可从干净 checkout 执行；备份、恢复和应用回滚步骤可由具备环境权限的操作者照文档演练。
- [ ] 每个子任务完成后执行与风险匹配的类型、规范、构建、集成测试或浏览器验证；最后在父任务做全量回归。

## Out of Scope

- P1/P2/P3 新业务能力，包括周期排课、独立报名、在线支付、家长端、经营分析和开放 API。
- 在未提供目标部署平台、备份仓库和生产凭据时实际写入外部备份或修改云端基础设施。
